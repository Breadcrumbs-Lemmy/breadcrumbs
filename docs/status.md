## Summary

The product center is "Where is my money going?" across all of one user's accounts and institutions. Both tiers now run and talk to each other: `apps/web` calls the single Fastify API in `packages/server` over HTTP, `packages/core` holds every calculation, and all five screen-facing endpoints serve real imported data. `packages/core` remains internal backend domain code with no browser runtime import.

The full loop has been exercised: CSV committed through the API, then the spending home, transactions, insights, and accounts screens rendered from that data in the browser. See "Verified End To End" below for what was actually run.

## Verified End To End

Run 2026-08-06 against a generated three-month single-account CSV (`mm/dd/yyyy` dates, quoted descriptions containing commas):

- `pnpm test` — 82 tests pass across `packages/core` (46) and `packages/server` (36).
- `pnpm build` — type-checks `core` and `server`, and builds the web bundle.
- **The whole flow in a browser, as a user:** Import → choose file → columns auto-suggested and confirmed → preview showed 63 valid rows with normalised merchants and correct signs → commit → every screen populated.
- Spending rendered week, month, and year totals; Transactions, Insights, and Accounts all rendered from the API.
- "Can I afford it?" derived a snapshot from that import — biweekly payroll, $1,450 rent, two subscriptions — and returned `AFFORDABLE` with a forecast timeline built from the user's own events.
- With no `ANTHROPIC_API_KEY`, the Assistant screen explains how to enable it and every other screen works unchanged.

**Not verified, and worth being plain about:**

- No **real bank export** has ever been imported. Every CSV so far was generated by us, which means it only proves the pipeline handles shapes we already anticipated.
- No **real PDF statement** has been transcribed. The extraction path is built and its safety property holds by construction (`CD-015` — the model's output goes through the same validation as a hand-mapped CSV), but its accuracy against a real bank layout is untested.
- The assistant has never been run against a live API key here.
- Docker images have never been built or run.
- Plaid has never been exercised against real Sandbox credentials.

## Risks To Track

- Advice boundary drift if AI explanations are added before deterministic outputs are stable.
- False precision in affordability answers if balances, pending transactions, or recurring schedules are incomplete.
- User trust loss if savings insights sound judgmental instead of practical and neutral.
- Plaid integration complexity if security, consent, and data deletion requirements are postponed too long.
- Plaid Sandbox scaffold currently uses an in-memory token store for local testing only; beta use needs encrypted persistence, authentication, deletion, and disconnect flows first.
- **Detectors that quietly read a field nothing writes.** The subscription panel reported zero over data full of subscriptions for as long as it existed, because `recurrenceSignal` was present on every fixture and absent from every import. Fixtures that hand-write a derived field will hide the derivation being missing. Anything read from a `Transaction` that is not written by both the CSV and Plaid mappers needs a test that starts from an import.
- **Capability flags in the UI going stale as the backend lands features.** `PERIOD_SUPPORTED` kept two working views switched off. A flag that says what the backend can do is a second copy of the truth, and it drifted.
